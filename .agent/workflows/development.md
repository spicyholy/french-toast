## 시작과 인수인계

1. 신규 프로젝트는 `architect`가 제품 요구사항 초안을 작성한다. 진행 중인 프로젝트는 PRD·API·ADR과 코드에서 변경의 진입점, 의존성, 사용자 흐름과 데이터 영향을 확인한다. 결함 수정이라면 변경 전에 가능한 범위에서 정상 진입점으로 문제를 재현하고 명령과 관찰값을 기록한다.
2. 화면 또는 사용자 상호작용을 만들거나 변경하면 `designer`를 호출한다. 디자인 결과를 반영한 기술 설계와 구현 명세를 `architect`가 작성한다. 작은 비UI 변경에도 근거와 검증 기준을 담은 명세를 준비한다.
3. `architecture_reviewer`에게 설계와 구현 명세를 독립 검토하도록 배정한다. 이후 전환은 아래 표를 따른다.

새 스레드에는 작업 ID, 사용자 의도와 범위, 관련 요구사항 ID와 정본 경로, 배정 파일, [변경본 식별 정보](../standards.md#변경본-식별과-검토-근거), 판단에 필요한 지적과 증거를 전달한다. 기존 스레드에서 이어갈 때는 최신 변경본, 달라진 내용, 처리할 지적을 보낸다. 독립 리뷰어에게는 스스로 판단하는 데 필요한 자료를 전달한다.

설계 수정은 `architect`, 제품 코드는 한 명의 `coder`, 테스트 스크립트와 실행 기록은 `tester`, 화면 산출물은 `designer`가 맡는다. 리뷰와 테스트가 진행되는 동안 `coder` 스레드를 유지한다. 기존 맥락이 유효하고 스레드를 사용할 수 있으면 구현 수정도 같은 스레드에 맡긴다. 같은 파일의 다음 쓰기는 이전 작성자의 결과를 확인한 뒤 배정한다.

리뷰어는 변경 작성자와 별도 스레드로 호출한다. 저장소를 읽기 전용으로 다루며 [검토 근거 규칙](../standards.md#변경본-식별과-검토-근거)에 따라 지적을 보고한다. 반론은 재현 가능한 근거로 기록하고 리뷰어에게 재확인받는다. 특정 지적의 수정 여부는 기존 리뷰어에게 확인받는다. 전제가 바뀌었거나 이견으로 독립적인 재평가가 필요하면 새 리뷰 스레드를 사용한다. 결과를 기록했고 맡을 일이 끝난 스레드는 정리한다.

## 판정과 다음 단계

| 판정 지점 | 조건 | 다음 단계 |
| --- | --- | --- |
| `architecture_reviewer` | `APPROVED` · 설계 승인 | `coder` → `code_reviewer` |
| `architecture_reviewer` | `REVISION_REQUIRED` · 설계 보완 | `architect`가 수정하거나 반론을 기록한다. UI 변경이 필요하면 `designer`를 경유하고 `architecture_reviewer`가 재검토한다. |
| `code_reviewer` | `APPROVED` · 코드 승인 | `tester` → `test_reviewer` |
| `code_reviewer` | `DESIGN_ISSUE` · 설계 또는 요구사항 문제 | `architect`가 설계를 다시 검토한다. UI 영향이 있으면 `designer`를 경유하고 `architecture_reviewer`부터 재진행한다. |
| `code_reviewer` | `IMPLEMENTATION_ISSUE` · 구현 또는 규칙 문제 | `coder`가 수정하고 `code_reviewer`가 재검토한다. |
| `test_reviewer` | `TEST_DEFECT` · 테스트 설계·코드·증거 결함 | `architect`가 평가 기준과 테스트 방식을 재검토한다. 이전 승인이 현재 입력에도 유효하면 `tester`부터 재진행한다. 승인이 무효가 됐다면 영향을 받는 가장 앞 단계로 돌아간다. |
| `test_reviewer` | `PRODUCT_FAILURE` · 재현 가능한 제품 결함 | `architect`가 원인을 판단한다. 설계 문제면 설계 검토부터, 구현 문제면 `coder`부터 재진행한다. |
| `test_reviewer` | `UNVERIFIABLE` · 필수 검증 실행 불가 | `architect`가 대체 환경이나 경로를 시도한다. 가능하면 `tester`부터 재진행하고 필수 검증을 끝낼 수 없으면 `BLOCKED`로 보고한다. |
| `test_reviewer` | `APPROVED` · 현재 변경본에서 필수 수용 기준과 회귀 검사가 통과했고 근거가 있음 | `architect`가 검증한 변경본, 현재 변경본과 문서를 대조한 뒤 일치하면 `PASS`로 보고한다. |

다음 단계를 배정하기 전에 해당 단계에 필요한 이전 승인이 현재 입력에도 유효한지 확인한다. 설계 문제와 구현 문제가 함께 발견되면 설계부터 처리한다. 요구사항·API·설계, 제품 코드, 테스트가 바뀌면 각각 설계 검토, 코드 검토가 이어지는 구현 단계, 테스트 단계 중 영향받는 가장 앞 단계부터 다시 진행한다. `architect`는 코드 리뷰의 제품 파일이 실제 테스트한 제품 파일과 일치하는지, 테스트 리뷰가 같은 제품·테스트 변경본의 실행 결과를 승인했는지 확인한다. 최종 대조에서 차이를 발견해도 이 기준으로 재진행한다.

## 재시도와 종료

- `architect`는 이전 단계로 돌아갈 때마다 재시도를 한 번 센다. 반론 재검토, 대체 환경 재실행, 변경본 불일치로 돌아가는 경우도 포함한다. 돌아간 뒤 정상 순서로 이어지는 단계는 같은 재시도에 포함한다. 재배정 전에 한도를 확인한다. 기본 6회를 허용하고 사용자가 한도를 지정하면 그 값을 쓴다. 같은 결함을 연속 두 번 수정해도 근거와 결과가 같거나 실질적인 해결 경로가 소진되면 중단한다.
- `PASS`는 필수 검사가 근거와 함께 통과했고 `test_reviewer`가 현재 변경본을 승인했을 때 사용한다. 해결되지 않은 확인된 결함이나 검토 이견은 `UNRESOLVED`, 환경·권한·필수 도구 부족은 `BLOCKED`로 보고한다. 재시도 한도에 닿으면 남아 있는 원인으로 상태를 결정한다.
- 서브에이전트 도구나 지정 역할을 로드할 수 없으면 앱·CLI에서 가용한 방법을 진단하고 준비를 계속한다. 필수 독립 검토가 불가능하면 해당 단계를 `BLOCKED`로 기록한다.
- 설치나 로그인이 사용자에게 필요한 경우 대상 이름, 공식 링크, 필요 이유, 영향을 받는 검증과 재개 방법을 전달한다. 독립적으로 할 수 있는 작업은 이어간다. 작업이 중단되면 최신 구현 명세, 관련 증거, 다음 단계, 누적 재시도 횟수를 인수인계 메모에 남긴다. 재개 시 이 메모와 현재 변경본을 대조한다.
