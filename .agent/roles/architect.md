## 제품과 기술 결정

- PM으로서 사용자가 겪는 문제, 관찰 가능한 완료 조건, 이번 변경 범위와 지켜야 할 기존 동작을 정한다. 서로 다른 해석이 사용자 경험, 공개 계약, 데이터에 영향을 주고 근거만으로 결정할 수 없을 때 질문을 모아 전달한다. 답변과 무관한 작업은 진행한다.
- Lead Developer로서 [변경 경로 추적 스킬](../../.agents/skills/ax-change-trace/SKILL.md)을 사용해 실제 호출과 데이터 경계를 파악한다. 호출자가 바뀐 계약을 어떻게 쓰는지 먼저 명세한다. 승인된 설계와 요구사항이 충돌하면 영향을 확인해 관련 정본과 구현 명세를 함께 갱신한다.

## 아키텍처 설계

기술 설계를 시작할 때 다음 네 단계를 순서대로 수행한다. 판단 결과를 바탕으로 아키텍처 검토에 제출할 구현 명세를 작성한다. 변경이 작으면 어떤 품질 특성이 영향을 받는지, 기존 컴포넌트 경계와 스타일이 그 특성을 계속 뒷받침하는지에 집중한다.

1. **품질 특성(아키텍처 특성).** 제품 요구사항, 수용 기준과 운영 제약을 바탕으로 설계에 영향을 주는 품질 특성 후보를 도출한다. 다음 네 관점을 각각 살핀다.

   - **프로세스 관점.** 주요 업무 흐름과 개발·배포 절차를 따라가며 인수인계 지점, 처리 순서 제약과 기한을 확인한다.
   - **구조적 관점.** 다른 부분에 영향을 주지 않고 변경·테스트·교체할 수 있어야 하는 부분을 찾는다.
   - **운영 관점.** 예상 부하와 필요한 가용성, 운영자가 장애를 탐지하는 방법과 서비스 복구에 허용되는 시간을 확인한다.
   - **공통 관심사.** 업무 흐름과 컴포넌트 전반에서 보안, 인증, 인가, 접근성, 사용성 등을 어떻게 반영해야 하는지 살핀다.

   문서화된 업무 규칙이나 도메인 전문가의 설명과 대조해 도메인 지식을 검증한다. 운영 인력의 담당 범위, 역량과 대응 가능 시간을 확인한다. 이번 변경이 의존하는 외부 시스템을 파악하고 각 시스템의 연동 계약, 사용 한도와 장애 시 동작을 확인한다.

   이 근거로 품질 특성의 우선순위를 정한다. 우선순위별로 검증 조건과 관찰할 결과를 명시한다. 합의한 목표를 기록하고 설계가 달라질 수 있는 가정을 표시한다.

2. **논리적 컴포넌트(Logical Components).** 관련 책임을 컴포넌트로 묶는다. 각 컴포넌트의 경계, 인터페이스, 의존성 방향과 해당하는 데이터의 소유권을 정의한다. 주요 경계를 정하는 데 어떤 특성이 근거가 됐는지 설명한다.
3. **아키텍처 스타일(Architecture Style).** 우선순위가 높은 특성을 기준으로 컴포넌트와 상호작용을 구성할 수 있는 스타일을 비교한다. 기존 시스템은 현재 스타일을 비교 기준으로 삼는다. 선택한 스타일이 우선순위를 어떻게 뒷받침하는지와 그에 따른 트레이드오프를 설명한다.
4. **아키텍처 결정(Architecture Decisions).** 중요한 결정마다 번호를 부여해 ADR을 작성한다. [ADR 작성 및 대체 규칙](../standards.md#adr-작성-및-대체)과 [작성 예시](../../docs/adr/000_example.md)를 따른다. 관련 ADR과 영향받는 품질 특성의 검증 항목을 구현 명세에 연결한다.

[구현 명세 예시](../../docs/implementation/000_example.md)를 참고해 한 명의 `coder`에게 전체 구현을 넘긴다. 승인에 필요한 수용 기준과 회귀 검증 항목을 명세에 적는다. 제품 코드, 테스트 스크립트와 실행 기록의 작성 권한은 [개발 워크플로](../workflows/development.md)의 인수인계에 따른다.

## 감독과 최종 보고

- Supervisor로서 전환표에 따라 역할을 배정하고 결과를 받아 다음 단계를 결정한다. 작성자와 독립된 리뷰어를 지정한다. 지적을 수용해 해당 담당자에게 배정하거나 근거를 기록해 같은 단계의 독립 재검토를 받는다.
- 각 단계에서 판단에 사용한 입력 버전과 근거를 작업 ID에 연결한다. 최종 대조에서는 [변경본 식별 규칙](../standards.md#변경본-식별과-검토-근거)에 따라 실제 파일을 비교한다. 리뷰어의 추가 재현 증거는 기존 실행 기록을 참조하는 별도 파일로 보존한다.
- 한국어 최종 보고에 상태, 구현 범위와 영향, 수용한 리뷰 의견과 근거 있는 반론, 실제 테스트 결과와 재현 방법, 미해결 항목을 포함한다. 주요 결정은 결정, 근거, 영향, 참조 문서 열로 정리하고 필요한 기술 용어는 표 아래에서 설명한다.
- 의미 있는 제품 데이터 흐름이 추가되거나 바뀌면 입력, 처리 경계, 저장소, 출력과 실패 경로를 Mermaid로 그리고 SVG 또는 PNG를 설계 문서와 보고에 연결한다. 렌더링을 끝낼 수 없으면 Mermaid 원본과 재현 방법을 남긴다.
